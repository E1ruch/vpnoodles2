# Перенос на новый VPS

Пошаговый чек-лист. Скрипт `migrate-vps.sh` (в корне проекта) закрывает только
перенос базы Postgres — самую опасную часть. Всё остальное здесь — руками,
по шагам ниже, в этом порядке.

Redis переносить не нужно: там только короткоживущие Redis-локи оплаты и кэш
статуса подписки (TTL — секунды/минуты). На новом сервере стартует пустым.

Remnawave-панель — отдельный внешний сервис, к этому VPS не привязана,
её вообще не трогаем.

## 0. Что должно быть на новом VPS заранее

- Docker + Docker Compose (v2: `docker compose version` должно отвечать)
- git
- nginx + certbot (или другой ACME-клиент), если бот работает через вебхук
  и/или используется веб-админка

## 1. Код

```bash
git clone <repo-url> vpnoodles2
cd vpnoodles2
```

`node_modules`/`dist`/`.env` в `.gitignore` — их тащить не надо, соберутся/появятся дальше.

## 2. `.env`

Не в git. Скопировать вручную со старого сервера, не пересоздавать из
`.env.example` — там реальные секреты (`TELEGRAM_BOT_TOKEN`, `REMNAWAVE_API_KEY`,
`YOOKASSA_SECRET_KEY`, `DATABASE_PASSWORD`, ...).

```bash
scp old-vps:/path/to/vpnoodles2/.env ./.env
```

Проверить на новом сервере значения, которые могут зависеть от порта/хоста
(`PORT`, `ADMIN_PORT`) — если на новом VPS эти порты чем-то заняты, поменяй
здесь, `docker-compose.yml` их подхватит сам (`ADMIN_PORT` уже параметризован
именно для этого случая).

## 3. Поднять Postgres и Redis (ещё БЕЗ приложения)

```bash
docker compose up -d postgres redis
```

Приложение (`app`) пока не поднимаем — чтобы оно не начало создавать пустые
таблицы/писать данные до того, как реальный дамп восстановлен.

## 4. Перенести базу

На **старом** сервере:

```bash
bash migrate-vps.sh --export
# → vpnoodles_backup_<timestamp>.sql.gz
scp vpnoodles_backup_*.sql.gz new-vps:/path/to/vpnoodles2/
```

На **новом** сервере:

```bash
bash migrate-vps.sh --import vpnoodles_backup_<timestamp>.sql.gz
```

Скрипт сам сверит количество строк в `users`/`subscriptions`/`payments`/`audit_logs`
после восстановления — сравни с тем, что он же вывел на старом сервере при `--export`.
Если в базе на новом сервере уже что-то есть (не пусто), он откажется писать
поверх без `--force` — это защита от случайного повторного импорта.

## 5. Собрать и поднять приложение — но пока без реального трафика

```bash
docker compose up -d --build app
docker compose logs -f app --tail 100
```

Проверить в логах: `Database connected`, `Redis connected`, `VPNoodles bot is running!`,
и что нет ошибок вида `EADDRINUSE` (порт уже занят) или `TELEGRAM_BOT_TOKEN` невалиден.

```bash
curl -s http://127.0.0.1:${PORT:-3000}/health
```

**Пока не переключай DNS и не останавливай старый сервер** — на этом этапе
новый инстанс уже может случайно начать long-polling к тому же боту, что и
старый, если оба одновременно активны. Держи это окно как можно короче
(шаги 5–7 подряд).

## 6. nginx + TLS

В репозитории конфига nginx нет — он живёт прямо на старом VPS
(`/etc/nginx/sites-available/...` или аналог). Варианты:

- Скопировать конфиг вручную (`scp`) и адаптировать под новый сервер (пути к
  сертификатам).
- Пересоздать заново и перевыпустить сертификат через `certbot` на новом сервере.

Важно (уже наступали на эти грабли — см. `CLAUDE.md`): домен для Telegram-вебхука
должен светить на `PORT` (обычно 3000), а НЕ на `ADMIN_PORT` (админ-панель).
Перепутаешь — Telegram будет получать 502 и молча переставать слать апдейты,
без единой ошибки в логах самого бота.

## 7. Переключение (момент даунтайма — минимизировать)

1. Остановить бота на **старом** сервере:
   ```bash
   docker compose stop app
   ```
   Именно остановить, а не оставить работать параллельно — два инстанса на
   одном токене (webhook или long-polling) конфликтуют.

2. Переключить DNS A-запись домена на IP нового сервера.
   Если бот работает через вебхук — сам URL (`TELEGRAM_WEBHOOK_URL`) не
   меняется, меняется только то, куда резолвится домен. DNS TTL определяет,
   сколько будет переходный период.

3. Проверить, что вебхук реально указывает туда, куда нужно:
   ```bash
   curl -s "https://api.telegram.org/bot<TOKEN>/getWebhookInfo"
   ```
   Смотреть на `url` и `last_error_message`.

## 8. Проверка после переключения

- `/start` в боте — приходит ответ
- Купить/продлить тестовую подписку — деньги проходят, дни начисляются
- Открыть админ-панель — авторизация через Telegram Login Widget работает
  (это единственное место, где реально нужен HTTPS от nginx)
- `bash migrate-vps.sh --verify` — числа в таблицах не меняются сами по себе
  без причины (значит, ничего не потерялось и не задвоилось)

## 9. Только после этого — гасить старый сервер

Дать постоять хотя бы день, последить за логами и платежами, и только потом
выключать старый VPS.
